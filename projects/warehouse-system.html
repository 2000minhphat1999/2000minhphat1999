Warehouse management system

An internal system for a manufacturing plant's production-engineering warehouse. It covers purchase-order intake, receiving, FIFO issue to production lines, returns, material classification, stocktake, monthly period closing and USD cost reporting.

Role
Developer: backend, PostgreSQL schema and SQL, data pipeline, web UI
Period
2025 – present (running in production, still being developed)
Users
Warehouse staff and production-line operators (not developers)
Stack
Python · Flask · PostgreSQL · psycopg2 · Alembic · Hypercorn · nginx · Jinja2 · htmx · SQLite · ReportLab

1 · Problem & constraints

The warehouse buys tooling, consumables, spare parts and safety equipment for several production lines. Purchase orders arrive as Excel files with prices in several currencies. Management needs stock and cost in USD, per material and per production line, with a clean month-end close.

The hard part is not CRUD. The same numbers are read by purchasing, the warehouse, line leaders and accounting, and a wrong number costs real money or real stock.

ConstraintConsequence for design
Users are warehouse staff, not engineersErrors must be shown in business language, next to the row that caused them, and fixable in place
Multi-currency purchase prices, USD reportingExchange rates stored per month; receiving is blocked when that month's rate is missing
Monthly and yearly closingClosing stock rolls into the next period's opening stock without double counting
Several people issuing and receiving at the same timeBatch allocation must be race-free
Offline plant networkNo CDNs: frontend libraries are vendored and Python packages are installed from local wheels
Business rules change often (e.g. a classification split mid-year)Rules must be written down once and imported, not copied

2 · Architecture

The system is a set of independent Flask applications, one per business module. Each runs as its own Hypercorn process on its own port, behind nginx, and they all share one PostgreSQL database. A long-running orchestration worker runs the intake pipeline and period-closing steps.

Trade-off of separate apps. Each module runs in its own process, so one module can be restarted without stopping the others. The cost is business logic duplicated across modules, covered in Limitations.

3 · Data model: four layers that must not mix

Most early bugs came from treating a derived number as if it were a stored fact. The model is now written down as four layers, and each layer may only be written by specific code.

LayerQuestion it answersWritten by
Master dataWhich material is this?Sync worker, keyed on (class, part_code)
DocumentsWhat was ordered, from whom, at what price?Excel upload
LedgerWhat happened? (receive, issue, return, scrap, transfer, stocktake, reclassify)Business routes, INSERT only
DerivedBatch balances, per-material stock and cost, period tablesReplay/recompute functions only
The main trap

The material table is both master data (code, class, unit) and a derived snapshot (closing stock, average cost). Editing a stock number there by hand does nothing useful: the next recompute overwrites it. To change a result, you change the ledger.

5 · Implementation

Intake pipeline

Goods do not enter stock through a single API. There are four stages, each with one owner:

  1. Upload — a 16-column Excel file goes into the purchase table. Values are cleaned on the way in (whitespace, Unicode). Each column is parsed in its own try, and unreadable numbers are stored as NULL with a note.
  2. Sync — the worker upserts materials keyed on (class, part_code) and validates classification, code and specification here, not at upload.
  3. Link — material IDs are written back to purchase rows, along with the pending-receipt quantity.
  4. Receive — the only step that creates batches and ledger rows. It sits behind four gates: a missing monthly exchange rate, a date outside the open period, open data-quality warnings, or receiving more than was ordered.

The orchestration worker runs stages 2–3 in a loop, detects when users have stopped entering data (20-second idle window on the ledger), then converts prices to USD and recomputes stock and cost.

Period closing

Month close recomputes the closing period, rolls each batch's remaining quantity into the next period's opening stock (assigned, not added, so nothing is counted twice), settles staged provisional issues, then recomputes both months again. Tooling tracked per user rolls over by year, and the yearly carry-forward does not depend on stocktake counts.

Supporting pieces

  • Session auth middleware shared by all modules, with per-account page permissions.
  • Four-state classification for production tooling (new / used / awaiting repair / awaiting scrap), rebuilt by replay from ledger rows and note labels.
  • Reorder quantity from lead time × safety stock − open orders − stock on hand.
  • A monitoring job that flags unusual daily receive/issue volumes against recent history. It is a warning tool only and never changes stock or cost.
  • PDF and Excel exports (ReportLab) that use the same labels as the UI.

6 · Difficult problems

1. The receiving gate said “clean” while bad rows were still there

Symptom
The warning flag flickered, warning files were deleted, and the logs kept reporting errors while the popup was empty. In the worst case, receiving was unlocked while invalid rows remained. This happened twice.
Root cause
Two blind spots. The detector trimmed and case-folded values before comparing, so it cleaned away the very errors it was meant to catch. And upload rejected rows it could not parse, so the detector never saw them.
Fix
Normalize only at the entrance (upload) and compare raw values everywhere after that. Upload never drops a row. The gate and the popup now scan the same scope with the same conditions.
Check
Deliberately leave one bad row that creates no duplicate. The gate must still report dirty and must not delete the warning file.

2. Changing a material's class reset its stock to zero

Context
The business split one classification into two, so existing materials had to change class without losing stock.
Root cause
Class is part of the business key (class, part_code), not a descriptive attribute. Changing it in only one table makes the sync worker create a new material ID with zero stock.
Fix
Reclassify across all six dependent tables in a single transaction.
Check
Simulated on a cloned database: COUNT(DISTINCT material_id) and total closing stock are identical before and after.

3. Rounding unit cost lost money

Context
Assembling a fixture issues its components by FIFO and receives the fixture at their combined cost. The fixture's cost must equal the sum of its parts exactly.
Root cause
When FIFO cuts across two batches at different prices and the quantity does not divide evenly, unit cost is a repeating decimal. Quantizing to 6 places lost −0.0000086 USD over 20 fixtures in simulation.
Fix
No rounding in cost paths. The numeric column has no scale limit, and totals are compared as Decimal, never float.
Check
Total cost before equals total cost after. The difference went from −0.0000086 to 0.

4. A “data loss” bug that was a misreading

Symptom
A batch showed Issued = −8 and Scrap = 0 even though items had been scrapped. It was reported as lost data.
Root cause
The four quantity columns on a batch cover the open period only. Issued is net of returns and can be negative. They are not lifetime totals.
Fix
No code change was needed. I documented the column semantics and added a diagnostic rule: find the open period before calling a batch wrong.
Lesson
Check the meaning of a number before “fixing” it. A fix here would have created a real bug.

5. Concurrent inline edits vs. receiving and issue design analysis

Finding
Stock issue already locks batch rows, but the admin inline-edit endpoint committed single cells with no version or staleness check. It could change a batch between a user opening a form and submitting it. Presence tracking (20-second heartbeat, 5-second polling) only warns and is not enforced by the backend.
Proposal
Stale-data warnings instead of auto-refreshing open forms. A row_version optimistic lock on purchase and batch rows (the material table can reuse updated_at). Backend guards that refuse edits while issue or receiving is active. Treat the ledger as non-editable.
Fallback
If migrations must wait, return a row fingerprint with each read and reject the update when it no longer matches. This is weaker than a version column but needs no schema change.

Algorithm check: specification history

One part code can map to several materials as its specification changes over time. Before adding a history table, I simulated 120 renames of one part code: a naive scan needs 214,320 comparisons, an indexed scan 3,750, and a compressed lineage 478. The conclusion: any long-term spec history must be index-first. The rule was documented before the runtime was changed.

7 · Verification

The codebase has no automated test suite yet, so every write path is verified in two ways:

  • Rollback simulation. Clone the database (CREATE DATABASE … TEMPLATE), open a transaction, call the real function, read the results inside the transaction, then roll back. Row counts of the target tables must match before and after, and the report states those counts.
  • Formula audit. Each stock and cost formula was written in business language and checked read-only against live data.

8 · Limitations & next steps

These are known limitations, listed because a reviewer would find them anyway:

  • Large route files. Some modules are a single file of up to ~180 KB with SQL inside the route handlers. There is no service or repository layer, so one business change can touch several modules.
  • Mirrored utilities. 13 helper modules exist in two locations and must be kept identical by hand.
  • Two migration systems (Alembic and hand-run SQL files).
  • No automated test suite. Verification relies on simulation scripts and compile checks.
  • One currency gap. The USD-only rule is not fully enforced yet: some conversion workers still fall back to the original price when a rate is missing. This needs a fix at the source.

What I would do next: extract ledger, FIFO and replay into one service module; wrap it in a pytest suite whose assertions are the written invariants; move to a single migration path; add row_version columns; and replace dynamic SQL identifiers with whitelisted psycopg2.sql composition.

9 · Lessons learned

  • Name the source of truth first. Once the ledger was the only writable fact, most “sync” bugs became replay calls.
  • Clean at the entrance, compare exactly inside. A validator that normalizes its input hides its own failures.
  • Business keys are not attributes. Know which columns form identity before letting users edit them.
  • Check comments against the query. Docstrings and old docs described a FastAPI/ORM architecture and a costing method that the code did not use. Only the executed query tells you what the code does.
  • Record decisions and failures. A rejected option such as Route B stays rejected because the reason is written down.
